# Deployment hosting and transactional email provider: Cloudflare Pages, Render, Resend

ADR 0011 deliberately left `apps/backend`'s PaaS host, `apps/web`'s static host, and (implicitly, via its "email verification is deferred" consequence) a transactional email provider as implementation-time picks, not architectural commitments. With #30 (frontend) and #18-#21 (backend) now built and #35 (the `uvicorn --factory` startup crash blocking any real deploy) fixed, this ADR resolves all three, informed by primary-source research at `docs/research/hosting-cost-options.md` and `docs/research/transactional-email-providers.md`.

**Decisions:**
- **Frontend static hosting: Cloudflare Pages.**
- **Backend + Postgres hosting: Render.**
- **Transactional email provider: Resend** (needed by #32's payment-first signup flow, which emails a password-setup link via fastapi-users' existing reset-password token mechanism — not needed by anything shipped today, decided now while other hosting picks were being made).

## Why

- **Cloudflare Pages over Vercel/Netlify:** costed against this app's real usage profile (10 users in month 1, growing to ~120 by month 12), Cloudflare Pages is free at every checkpoint with no bandwidth cap and a 100,000-requests/day Functions allowance thousands of times this app's real volume. Vercel was ruled out on a term-of-service ground, not a technical one: its free Hobby tier's own docs state it "restricts users to non-commercial, personal use only" (verified directly against `vercel.com/docs/plans/hobby`), and this becomes a paid product under ADR 0013 (Website Access / Android Access / OCR Credits are real Stripe purchases) — so Vercel would require its $20/month Pro tier from day one regardless of traffic. Netlify's free tier is plausibly usable but shares one 300-credit pool across bandwidth, requests, *and* deploys, meaning active development competes with real user traffic for the same budget — a subtler, ongoing risk Cloudflare doesn't carry.
- **Render over Railway/Fly.io for backend + Postgres:** Fly.io is ruled out on cost, not preference — its supported Managed Postgres has no free tier and a $38/month floor regardless of database size or traffic (verified directly against `fly.io/docs/mpg/`), an order of magnitude more than the other two for a database that will stay well under 1GB for years at this scale. Railway and Render land close in raw dollars (~$8-18/month either way), so the deciding factor was predictability: Render prices compute and Postgres as fixed, nameable line items, so the monthly cost is knowable in advance. Railway meters everything (backend container and Postgres alike) against one shared, usage-driven credit pool, so the bill depends on actual RAM/CPU consumption rather than a quoted plan price. Given this project's own established instinct toward bounding cost exposure (ADR 0013's OCR Credit balance cap exists for exactly this reason), Render's fixed pricing was judged the better fit even though the two options are close on raw cost.
- **Resend over Postmark/SendGrid/AWS SES/Mailgun:** per `docs/research/transactional-email-providers.md`'s existing recommendation (SendGrid's free tier was discontinued; AWS SES needs more setup for a project this size; Mailgun ranked behind the other two). Postmark was the other finalist; Resend was picked as the simpler integration for a single email type (password-setup links via fastapi-users' reset-token flow) with no other email needs identified yet.
- **The planned Android client does not change any of the above.** Evaluated explicitly: a REST API is client-agnostic, so Android hitting the same endpoints as `apps/web` today adds no new hosting requirement beyond what the web frontend already needs (a stable, public, HTTPS-reachable backend). CORS — the main thing distinguishing web's requirements from a native client's — doesn't apply to Android at all. The one real Android-readiness question is **application-level, not a hosting one**: `apps/backend`'s session-cookie auth (fastapi-users' `CookieTransport`, per ADR 0011) is workable but not the idiomatic pattern for a native app (bearer tokens usually are) — left as its own future consideration when Android work starts, independent of this ADR.

## Considered options

- **Railway** (backend+Postgres). Rejected in favor of Render: no dedicated free/cheap Postgres allowance — the database is metered under the same shared usage pool as the backend container, so the effective monthly cost is a moving number rather than a quoted plan price. Not rejected on pure dollar cost (the two are close); rejected on predictability given this project's stated preference for bounding cost exposure.
- **Fly.io** (backend+Postgres). Rejected on cost: Managed Postgres has no free tier and a $38/month floor independent of actual database size or traffic — the only cheaper path is Fly's own explicitly deprecated, unsupported self-run Postgres option, not worth the risk for a real product.
- **Vercel** (frontend). Rejected: free Hobby tier's terms of use disqualify a commercial product from day one, forcing a $20/month Pro seat regardless of how little traffic this app generates.
- **Netlify** (frontend). Rejected: plausibly free through month 12, but its single shared credit pool (bandwidth + requests + deploys) means active development competes with real traffic for the same budget — a real, ongoing risk Cloudflare's model doesn't have.
- **Postmark** (email). Rejected, not on cost or reliability (both are close to Resend on the research doc's own findings) — Resend's integration is simpler for this project's single, narrow email need.

## Consequences

- **Render's free tiers are not viable for a real deploy and must not be used.** The free web service sleeps after 15 minutes of inactivity with a ~1-minute cold start on the next request — a real UX problem for a login-based app. The free Postgres tier auto-deletes 30 days after creation (14-day grace period) — using it for real user data would silently lose it. The real deploy must use Render's paid Starter web service (~$7/month) and a paid Basic Postgres instance (~$6/month) from the start.
- **`apps/backend`'s `cookie_secure=False` (hardcoded in `app.py`, per its own comment "tighten to True once this is actually served over HTTPS") must be flipped to `True` before this goes live** — Render terminates TLS, so the app will be served over real HTTPS, and the session cookie should require it.
- **A custom domain (not Render's/Cloudflare's default throwaway subdomain) should be set up before any Android client ships**, so the API's base URL is stable — an app-store-distributed client can't be redirected to a new backend URL as easily as a web SPA's env var can be changed. Not urgent for the current web-only deploy, but cheap to do now rather than retrofit later.
- **Environment variables/secrets needed for the real deploy** (not yet set anywhere): `TOWING_BACKEND_SECRET` (a real value, not the dev fallback #33 already warns about), `TOWING_BACKEND_CORS_ORIGIN` (the real Cloudflare Pages URL), `TOWING_BACKEND_DB_URL` (Render's real Postgres connection string), and a Resend API key once #32 is implemented.
- **This decision is reversible but not free to reverse** — `apps/backend`'s storage-Protocol seam (ADR 0008) and standard Postgres wire compatibility mean switching PaaS hosts later doesn't require an architecture change, but does mean real migration work (DNS, secrets, potentially a data export/import). Treat this as a sticky decision, not a permanent one.
- **Resend is picked ahead of #32's implementation** — #36 (the pricing/business numbers #32 itself left open) is unaffected by this ADR; choosing a provider doesn't require settling on OCR Credit prices or the balance cap ceiling.
