# Paywall: free anonymous calculator, paid persistence, separately-metered OCR credits

The web app's calculator (compute only, no saving) stays fully anonymous and free, matching the existing Streamlit deployment — no Account is created until someone pays. A one-time **Website Access** purchase unlocks persistence (saving Garage profiles and Weigh Event history) and grants a starter allotment of **OCR Credit**; a one-time **Android Access** purchase is a superset that also unlocks the Android client, with no discount for a prior Website Access purchase. OCR Credit is metered 1:1 against each Claude-vision API call (matching the existing per-photo adapter calls exactly), sold separately in 6-credit bundles, never expires, but is capped at a configurable outstanding-balance ceiling — purchases that would exceed the cap are blocked before Stripe is charged, to bound Anthropic API cost exposure on credits that will never expire. A zero balance degrades gracefully to the existing manual-entry path rather than blocking the flow. Signup is payment-first: Stripe Checkout collects only an email, the Account (already paid, with its Garage auto-provisioned per ADR 0010) is created by the payment webhook, and the user sets a password afterward via an emailed link — #18's registration flow runs in reverse order for paying users.

## Considered Options

- **Requiring an Account (even a free $0 tier) before using the calculator at all.** Rejected — the calculator has no persistence to protect and no OCR cost to gate, so there's nothing an anonymous user could abuse; forcing signup would only add friction to the free path.
- **Selling OCR Credit to anyone, without requiring Website/Android Access first.** Rejected — a credit is only useful attached to a save-capable flow in practice, and gating it behind an existing paid tier avoids building a standalone unauthenticated purchase/entitlement path for a case that wouldn't otherwise arise.
- **Prorating an upgrade from Website-only to Android.** Rejected in favor of full price, no discount — avoids building a purchase-history-aware pricing calculation for what's expected to be a rare edge case; accepted explicitly as a known simplification.
- **Letting credits expire.** Rejected — no expiry-tracking field, no "why did my credits vanish" support burden. The real cost-exposure risk (rising Anthropic prices against a large non-expiring balance) is handled by the outstanding-balance cap instead of expiration.
- **A lifetime purchase cap instead of an outstanding-balance cap.** Rejected — a lifetime cap permanently locks out the heaviest users once hit, even after they've spent their entire balance to zero. An outstanding-balance cap bounds exposure at any point in time while still letting a user spend down and buy again indefinitely.
- **Granting partial credits when a purchase would exceed the cap, instead of blocking the purchase.** Rejected — charging full price for a bundle and delivering fewer credits than paid for is the kind of mismatch that generates chargebacks and support tickets; blocking the purchase before Stripe is charged is the only option that never takes money for something not delivered.

## Consequences

- The backend needs the Stripe webhook to be the actual account-creation trigger, not the registration endpoint #18 originally specified — #18's spec needs revisiting for paying users (whether a separate no-payment registration path still exists, e.g. re-sending a password-setup email, or is dropped entirely).
- Every OCR-credit-consuming endpoint needs an atomic conditional decrement (not a separate read-then-write), both to stay race-safe under concurrent requests and to correctly enforce the cap at purchase time.
- Exact price points, starter-credit counts, and the balance-cap ceiling are deliberately left unset — recorded as pricing decisions to make at implementation or launch time, not architecture blockers.
