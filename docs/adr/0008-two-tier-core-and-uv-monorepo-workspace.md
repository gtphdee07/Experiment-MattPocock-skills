# Two-tier core (compute vs application-services) in a `uv` monorepo workspace

The towing weight-limit logic was a single flat `towing_app` package with `argparse`, `print()`, and `input()` woven through every layer, so nothing above the pure calculation functions could be reused by the planned Streamlit calculator, FastAPI backend, or Android app. We split the code into two library tiers plus a client tier, all members of one `uv` workspace with a virtual (project-less) root: `packages/towing-core` (imported `towing_core`) is the dependency-free compute tier — domain models, the six overload calculations, Rig Evaluation, and the storage + field-acquisition **ports** (Protocols) with their in-memory implementations; `packages/towing-app` (imported `towing_app`) is the application-services tier — Weigh Event orchestration, Nickname snapshotting, persistence coordination, and the concrete adapters (`Sqlite*Store`, the `anthropic`-backed Claude-vision field sources, the web axle-count lookup); `apps/cli` (imported `towing_cli`) is the interactive client. The dependency arrow only ever points down: `towing-core` depends on nothing, `towing-app` depends on `towing-core` plus third-party adapters, `apps/*` depend on `towing-app`, and nothing depends on `apps/*`. Every future surface picks its tier — Streamlit will import `towing-core` only (no `anthropic`), the backend will use both.

## Why the seam falls where it does

The split is by *dependency purity and reuse*, not by "domain vs plumbing". A Protocol and its in-memory fake are pure Python with no third-party imports and are needed by every surface (including tests and the Streamlit calculator), so `TruckStore` / `TrailerStore` / `WeighEventStore` / `WeighEventRecord` / `InMemory*Store` and the `FieldSource` / `TextFieldSource` ports live in `towing-core`. The concrete implementations pull in `sqlite3` or `anthropic` and are only wanted by the stateful surfaces, so `Sqlite*Store` and the `ClaudeVision*` / `WebAxleCount*` adapters live in `towing-app`. This is what makes the surprising-looking pairing deliberate: **storage Protocols in core but SQLite in the app tier; field-acquisition Protocols in core but the `anthropic` concretes in the app tier.**

## Considered options

- **Keep one flat package.** Rejected: the Streamlit app would have to install `anthropic` and drag in the SQLite stores it never calls, and there would be no enforced boundary stopping compute code from growing a `print()` or an `import anthropic` again.
- **Three or more packages** (e.g. a separate `towing-storage`, `towing-vision`). Rejected as premature: the app tier is small and cohesive, and more packages means more `pyproject.toml` files and version churn for no current benefit. Revisit if the backend needs a store implementation the CLI must not pull in.
- **A real (non-virtual) workspace root package.** Rejected: there is no top-level thing to ship — the root exists only to host `[tool.uv.workspace]` and the shared `ruff` / `mypy` / `pytest` config. A virtual root keeps `uv sync` from building an empty wheel.

## Consequences

- `towing_core` has an enforced import-direction guard: `packages/towing-core/tests/test_layering.py` parses every core source file with `ast` and fails if it imports `anthropic`, `sqlite3`, `argparse`, `streamlit`, `towing_app`, or `towing_cli` (and a matching check keeps `towing_app` out of the client tiers). The tier boundary is a test, not a convention.
- Shared tool config lives once at the workspace root (`[tool.ruff]`, `[tool.mypy]`, `[tool.pytest.ini_options]` with `testpaths` spanning all three members). One `uv.lock`, one `.venv`, one `uv run pytest` across the whole repo.
- Each package carries its own `hatchling` build backend and a `py.typed` marker so `mypy --strict` resolves exported types across the package boundary.
- `OverloadStatus.NEAR_LIMIT` exists as an enum value in `towing_core.evaluation` even though only Trailer GVWR Overload can currently produce it (ADR 0006). The enum is the shared vocabulary every surface colors values by; scoping the *value* out to match today's single producer would just force a later additive change when another check gains a margin.
- The moved `resolve_db_path` / `DEFAULT_DB_PATH` / `DB_PATH_ENV_VAR` are byte-identical to their pre-refactor form — only their file location changed (`towing_app/cli.py` → `towing_cli/cli.py`). The shipped CLI's real data path (`~/.towing_app/garage.db`) is unchanged.
- The CLI *command* stays `towing-app` (`[project.scripts]` in `apps/cli`) while the `towing-app` *distribution* is the services tier. This name overlap is deliberate (muscle memory) and flagged as revisitable when the backend phase starts — rename the command to `towing` then if it proves confusing.
