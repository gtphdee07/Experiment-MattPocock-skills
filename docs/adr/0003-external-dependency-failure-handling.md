# External dependency failures degrade to manual entry, with failure-type-aware messaging

Ticket #4 (Claude-vision OCR) initially handled all extraction failures — a bad photo, a missing API key, a network outage — identically: catch, return `None` for every field, and tell the user "Could not read X from the photo." That conflates two different problems. A missing/invalid key or a network/server failure means the service was never reached at all; the photo may be perfectly fine. Telling the user to blame their photo when the real cause is a credential or connectivity problem wastes their time and, worse, becomes actively misleading once real money is on the line — future tickets involving payment processing or account lookups can't afford to tell a user "your card looks wrong" when the real problem was our own payment gateway being unreachable.

We're splitting these into two distinct outcomes: a **content failure** (the service was reached, responded, but couldn't determine one specific value — e.g. a genuinely blurry field) still returns `None` for just that field, prompting the user to fill in that one value manually, same as before. A **service failure** (the call couldn't complete at all — bad or missing credentials, network failure, timeout, server error, rate limit) is raised as a distinct `FieldSourceUnavailableError`, causing the caller to abandon the photo-based flow entirely and switch straight to full manual entry, with a message that says the *service* was unreachable, never implying anything about the photo. No automatic retry in v1 — a transient failure just means the user re-runs the command; this is a low-frequency, low-stakes CLI flow where retry logic isn't worth the complexity yet.

**Consequences**: any future external dependency (a manufacturer GCWR lookup, and eventually payment/account calls) should follow this same shape — a distinct "the dependency itself is unavailable" signal, separate from "it responded but couldn't give me this value," with user-facing messaging that names which one happened. Payment and account-lookup dependencies will need to revisit this with more rigor than v1's policy gives — idempotency and double-charge prevention aren't covered here, and shouldn't be bolted onto this simpler policy without deliberate design when those land.
