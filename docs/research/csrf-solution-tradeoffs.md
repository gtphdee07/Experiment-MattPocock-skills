# CSRF solution tradeoffs — closing issue #40

**Status:** research only — no decision has been made. This document exists so a human can *decide how* to close [issue #40](https://github.com/gtphdee07/Experiment-MattPocock-skills/issues/40), informed by primary-source facts as of **2026-09-19**.

**Relationship to `docs/research/csrf-protection-options.md`:** that document already did the primary-source legwork comparing `fastapi-csrf-protect` vs `starlette-csrf` vs hand-rolling vs Origin/Referer checking against this exact codebase, and recommends `starlette-csrf` as middleware. This document treats those findings as a trusted input (cited as "per `csrf-protection-options.md` §N" throughout, not re-verified) and widens the lens: instead of "which CSRF-token library," it lays out the *actual range* of solutions — including one that removes the CSRF attack surface structurally instead of mitigating it with a token — organized the way a decision-maker needs it: cost, safety, and a middle path, each scored on the same four dimensions.

**Recap of the gap** (see the prior doc's own recap for full detail): `apps/web` (Cloudflare Pages) and `apps/backend` (Render) are on different registrable domains — genuinely cross-site (ADR 0016). That forced fastapi-users' session cookie from `SameSite=Lax` (implicit CSRF protection) to `SameSite=None` (paired with `Secure`, via `TOWING_BACKEND_COOKIE_SECURE`) in `apps/backend/towing_backend/app.py`'s `CookieTransport` construction (lines 93–108). CORS (`allow_origins=[settings.cors_origin]`) doesn't help — it's a response-reading control, not a request-sending one. Today, any site a signed-in Account visits can fire a blind `fetch(..., {credentials:'include'})` against `DELETE /users/me`, `POST /trucks`, `POST /weigh-events`, etc., and it executes server-side.

---

## The three options at a glance

1. **Cheapest, ships fastest:** `starlette-csrf` middleware with `sensitive_cookies` pinned to the session cookie.
2. **Safest, most architecturally correct:** switch fastapi-users' auth transport from `CookieTransport` to `BearerTransport`+`JWTStrategy`, removing ambient-credential attachment (the actual mechanism CSRF exploits) rather than mitigating it — evaluated head-to-head against the OWASP-aligned stateful synchronizer-token alternative that keeps cookies.
3. **Credible middle path:** `starlette-csrf` middleware **plus** Origin/Referer-header verification, layered as defense-in-depth — cheaper than option 2, materially more robust than option 1 alone.

Each is developed in full below, then compared in one table.

---

## Option 1 — `starlette-csrf` middleware (cheapest, ships fastest)

### Why this wins "cheapest" over the alternatives in this slot

Two real candidates exist for "lowest cost, ships soonest": `starlette-csrf` middleware, and Origin/Referer-header verification alone. Comparing them directly on the requested axes rather than just restating the prior doc's overall pick:

| | `starlette-csrf` middleware | Origin/Referer check alone |
|---|---|---|
| New dependency | None — `itsdangerous` already resolved in `uv.lock` at 2.2.0 transitively (per `csrf-protection-options.md` §3) | None |
| Lines of code touched | ~1 `app.add_middleware(...)` call in `create_app()` (per §4 of the prior doc) | A tiny custom middleware/dependency (~15–20 lines: read `request.headers.get("origin")`, fall back to `referer`, compare host to `settings.cors_origin`, reject on mismatch) — this repo doesn't have one today, so it's new code, not a config call |
| Files touched | `apps/backend/towing_backend/app.py` only | `apps/backend/towing_backend/app.py` (new middleware function/class) — plus the *frontend* needs zero changes either way, since neither approach requires a new client-side header (Origin/Referer are browser-attached automatically, not app-set) |
| Frontend changes | **Yes** — `apps/web/src/api.ts`'s `request()` helper needs to read a token and attach a header on every mutating call (prior doc §4, item 2) | **None** — the browser sets `Origin`/`Referer` itself; no client code changes at all |
| Coverage of fastapi-users' own routes (`POST /auth/logout`, `PATCH /users/me`) | Full — middleware wraps every route uniformly (prior doc §2/§4) | Full — same reason, it's also middleware-shaped |
| Residual gap | None material once wired (see Risk section below) | `Origin` can be absent on some redirects; `Referer` is stripped by privacy settings/some proxies (OWASP, quoted in prior doc §5c) — a real, if narrow, bypass surface |

**Origin/Referer checking is actually the cheaper build** (no frontend change, less code review surface on the security-sensitive comparison logic being smaller) — but it is explicitly a defense-in-depth measure, not a substitute for a token, per OWASP's own Cross-Site Request Forgery Prevention Cheat Sheet: the Synchronizer Token Pattern section frames header/token checks as the primary control, and the cheat sheet's own verifying-origin section (cited already in the prior doc §5c) calls out real bypass gaps. Given issue #40 asks to *close the gap*, not add a partial mitigation, shipping Origin/Referer checking *alone* would leave the core exploit (forged state-changing request with the ambient cookie attached) only probabilistically blocked, not closed. **`starlette-csrf` is therefore the answer for this slot** — it is a fully worked, already-tested 136-line implementation (prior doc §5b) that a single `add_middleware()` call adopts wholesale, and it actually closes the gap rather than narrowing it. Origin/Referer checking is folded into Option 3 as the "add a second cheap layer" middle path instead of being sold here as a complete answer.

### Pros
- Single middleware call, no per-route wiring; automatically covers fastapi-users' own `/auth/logout` and `/users/me` routes that a per-route library (`fastapi-csrf-protect`) structurally cannot reach (prior doc §2, confirmed against `fastapi_users/router/auth.py` — those routes are closures inside `get_auth_router()`, never visible to `app.py`).
- Zero net new dependencies (`itsdangerous` already resolved).
- `sensitive_cookies={COOKIE_NAME}` naturally exempts `/auth/login`/`/auth/register` (no session cookie yet) while protecting everything issued a session (prior doc §4).
- Built by the fastapi-users maintainer (frankie567) specifically as his answer to "how do I add CSRF to fastapi-users" (fastapi-users discussion #291, cited in prior doc §2) — the closest thing to an officially-blessed answer that exists.

### Cons
- Last PyPI release **2023-06-27** (3.0.0), 6 open GitHub issues, vs. `fastapi-csrf-protect`'s more recent cadence (prior doc §3) — a real, if judgment-call-sized, maintenance-staleness risk.
- Its CSRF cookie needs the identical `SameSite=None; Secure` treatment as the session cookie (prior doc §1) — it does not sidestep the cross-site cookie problem, it adds a second cookie subject to the same browser rules.
- Frontend work is real, not zero: `apps/web/src/api.ts`'s `request()` helper (lines 45–80) needs to read the CSRF cookie value (readable directly since `starlette-csrf`'s cookie defaults `cookie_httponly=False`, per `middleware.py`) and attach it as a header on every mutating call, plus a custom exception handler so a `starlette-csrf` 403 (plain text by default) matches the JSON `{"detail": ...}` shape `ApiError` already expects (prior doc §4).
- Still fundamentally a *mitigation* bolted onto an architecture (ambient cookie auth) that creates the exposure in the first place — it doesn't remove the underlying mechanism, it detects forgery attempts against it.

### Impact to the current baseline
- **Files changed:** `apps/backend/towing_backend/app.py` (one `add_middleware(CSRFMiddleware, ...)` call plus a small exception handler for 403 shape), `apps/backend/pyproject.toml` (add `starlette-csrf` as an explicit dependency even though its own transitive dep is already present), `apps/web/src/api.ts` (`request()` reads/attaches the CSRF header).
- **ADRs:** none need amending — this doesn't touch ADR 0011's session-cookie decision or ADR 0015's async boundary; it's additive.
- **Tests:** `apps/backend/tests/test_http_auth_flow.py` and every HTTP-level test file that calls mutating routes (`test_http_truck_trailer_profiles.py`, `test_http_weigh_events.py`, `test_photo_ocr_endpoints.py`, `test_cookie_security.py` — 12 files import or use the `register`/`login` helpers per a repo-wide grep) will start **failing** the moment the middleware is wired, because `TestClient`'s cookie jar doesn't know to mint or resend a CSRF header — every test that currently does `client.post(...)`/`client.patch(...)`/`client.delete(...)` after `login()` needs a helper update to fetch and attach the token. This is mechanical (one shared helper change in `test_http_auth_flow.py`'s `register`/`login` functions plus verifying the other 11 files' fixtures flow through it) but real, non-zero work — not a rewrite of test *intent*, just plumbing.
- **Cookie invalidation on rollout:** no — existing session cookies keep working; the CSRF cookie is a new, independent cookie issued on next login/request, nothing to invalidate.

### Time to implement
**Small — roughly 0.5–1 day.** Middleware wiring is ~30 minutes; the bulk of the time is the `api.ts` change, the JSON-shaped exception handler, and updating the ~12 test files' shared login/request helpers to carry the CSRF header through.

### Risk/exposure relative to the safest option (Option 2)
Once wired correctly, `starlette-csrf` closes the *same* class of attack Option 2 closes (a third-party site can no longer successfully replay a forged state-changing request, because it cannot read the CSRF cookie's value to echo it back in the header). The residual gap relative to Option 2 is narrower and different in kind:
- **The credential itself is still an ambient cookie.** If an attacker achieves **any** form of cookie theft or a same-site subdomain compromise (not classic cross-site CSRF, but session-fixation-adjacent or cookie-jar-sharing attack classes), the session cookie remains usable exactly as before — Option 2 doesn't have a *session cookie* to steal in the same way (see Option 2's own honest XSS caveat below, though — it's not risk-free either).
- **New dependency risk moved, not removed.** A 3-year-stale, 6-open-issue dependency is now in the security-critical path. If a real vulnerability is ever found in `starlette-csrf`'s comparison logic (e.g. a timing side-channel, since its cookie comparison hasn't been audited as heavily as fastapi-users' own core), there's no active upstream to patch it quickly — a human would need to fork or hand-patch. Option 2 has no equivalent library-risk surface (fastapi-users' own `BearerTransport`/`JWTStrategy` are actively maintained, first-party to the auth library already in use).
- **Concrete attack scenario still theoretically open:** none within CSRF's own threat model once wired correctly — this is a real, complete fix for the stated issue, not a partial one. The gap named above is about *dependency risk* and *credential-theft-adjacent* attack classes, not "CSRF still works."

## Option 2 — Structural fix: `BearerTransport` + `JWTStrategy` (safest), vs. the stateful synchronizer-token alternative

The task calls for evaluating **two** candidates for "safest" against each other: eliminating ambient-cookie auth entirely (Bearer/JWT), and the OWASP-aligned stateful synchronizer token tied to the existing `AccountSession` row (a cookie-preserving option). Both are developed fully, then compared.

### 2a. Switching to `BearerTransport` + `JWTStrategy`

**What CSRF actually exploits, and why this removes it structurally:** CSRF works because browsers *automatically* attach cookies to any request to the cookie's domain, regardless of which page initiated the request. An `Authorization: Bearer <token>` header is never attached ambiently by a browser — it only appears on a request if the requesting page's own JavaScript explicitly set it. A third-party page cannot make the victim's browser attach a header it has no way to read or construct. This isn't a mitigation of the CSRF mechanism, it's removal of the precondition CSRF requires. This structural reasoning is not something either library's docs states explicitly as "solves CSRF" (checked directly — see below), but follows directly from the transport's own mechanics as documented and sourced.

**Primary-source findings on `BearerTransport`** (fetched directly from `fastapi_users/authentication/transport/bearer.py` and the official docs at `fastapi-users.github.io/fastapi-users/latest/configuration/authentication/transports/bearer/`, both 2026-09-19):
- Constructor: `BearerTransport.__init__(self, tokenUrl: str)`, wrapping `OAuth2PasswordBearer(tokenUrl, auto_error=False)` — the token is read from the `Authorization` header only; there is no cookie involved anywhere in this transport.
- `get_login_response(token)` returns `JSONResponse({"access_token": token, "token_type": "bearer"})` (a `BearerResponse` model) — the frontend receives the raw token in the response **body**, not a cookie, and is responsible for storing and resending it.
- `BearerTransport` explicitly does **not** support logout — calling logout raises `TransportLogoutNotSupportedError()`, confirmed directly in the source. This is a real gap versus the current `POST /auth/logout` behavior: with a stateless JWT there is nothing server-side to revoke, so "logout" becomes purely a client-side "forget the token" action unless paired with a server-side revocation list (see below).
- The **official docs' own transport-comparison table** (fetched directly, 2026-09-19) states plainly: Cookie transport's con is "**Needs a CSRF protection for maximum security**"; Bearer transport's con is "**Needs to be stored manually somewhere in the client**." Cookie's recommended use case: "implement a web frontend." Bearer's recommended use case: "implement a mobile application or a pure REST API." **This is a real, named tradeoff directly from fastapi-users' own docs, not this document's inference** — the library's authors frame Bearer as the non-CSRF option and Cookie as the option that needs a CSRF add-on, but they also frame Bearer as intended for non-browser or API clients, not a browser SPA like `apps/web`, without further comment on why.

**`JWTStrategy` findings** (fetched directly from `fastapi_users/authentication/strategy/jwt.py`, 2026-09-19):
- Constructor: `JWTStrategy(secret, lifetime_seconds, token_audience=["fastapi-users:auth"], algorithm="HS256", public_key=None)`.
- `write_token` builds `{"sub": str(user.id), "aud": self.token_audience}` and signs it — a **stateless** token; nothing is written to `AccountSession`/`sessions` at all when using `JWTStrategy` instead of `DatabaseStrategy`.
- `destroy_token` raises `JWTStrategyDestroyNotSupportedError` with the message (paraphrased from source comment) that "a JWT can't be invalidated: it's valid until it expires" — **this is the single biggest architectural consequence of this option**: today, `DELETE /users/me` and `POST /auth/logout` cascade-delete or otherwise remove the `AccountSession` row (`test_delete_me_removes_account_garage_and_session`, `test_logout_revokes_the_session_cookie` — both currently-passing tests depend on this), immediately invalidating the session server-side. A pure `JWTStrategy` cannot do this: a stolen or leaked token remains valid until its `lifetime_seconds` expiry regardless of logout/account-deletion, unless a revocation mechanism (e.g. a denylist table, or keeping `DatabaseStrategy`'s session row *and* wrapping it for Bearer transport — fastapi-users' `AuthenticationBackend` actually decouples transport from strategy, so `BearerTransport` + `DatabaseStrategy` is a real, valid, supported combination that keeps server-side revocability while dropping the ambient-cookie transport) needs to be added.

**The honest XSS-vs-CSRF tradeoff this option creates** (the prompt is explicit that this must be weighed honestly, not glossed over): today's `httponly` session cookie (implied by fastapi-users' `CookieTransport` defaults, not overridden in `app.py`) is **not readable by JavaScript at all** — even a successful XSS injection on `apps/web` cannot exfiltrate the session cookie directly (though it could still *ride* the cookie to make authenticated requests from the victim's own browser, which is its own real risk, just a different one than exfiltration). A Bearer token, by contrast, **must** be readable by `apps/web`'s own JavaScript to be attached to the `Authorization` header on every request — meaning it must live somewhere JS can reach: `localStorage`, `sessionStorage`, or an in-memory JS variable. All three are directly readable by any successfully-injected XSS payload, in a way the current `httponly` cookie is not. In-memory storage is the least-bad of the three (survives no page reload, gone on tab close, never touches persistent storage) but still readable to any script running on the page at the moment it exists. **This is a real, named regression in one attack surface (XSS-driven token theft) traded for elimination of another (CSRF)** — not a strict security improvement, a different risk profile. This tradeoff is fastapi-users' own docs' framing too (Cookie: "needs CSRF protection"; Bearer: "needs to be stored manually" — the docs don't spell out the XSS implication of that manual storage, but the mechanism is the same one described here, verified directly against the transport source, not inferred from the docs' brevity).

**What the migration actually requires in this codebase:**
- `apps/backend/towing_backend/app.py`: swap `CookieTransport(...)` for `BearerTransport(tokenUrl="auth/login")`; if server-side revocability is kept (recommended, given the two tests above), keep `DatabaseStrategy`+`AccountSession` and only change the transport, not the strategy — fastapi-users' `AuthenticationBackend(transport=..., get_strategy=...)` cleanly decouples the two, confirmed by the source's own composition (`AuthenticationBackend` takes both independently).
- `apps/web/src/api.ts`: `request()`'s `credentials: 'include'` becomes irrelevant (no cookie to send) and is replaced with reading a stored token and setting `Authorization: Bearer <token>` on every call; `login()` must now parse the JSON body for `access_token` and store it (localStorage/sessionStorage/memory — a real design decision with the XSS tradeoff above); every one of the ~15 exported functions in `api.ts` that currently rely on the browser's automatic cookie attachment needs no *individual* change (they all funnel through `request()`), but `evaluate()` (the free calculator, `apps/web/src/api.ts` lines 85–93) already bypasses `request()` entirely and stays untouched, correctly, since it's unauthenticated.
- **Every call site is affected indirectly** through the shared `request()` helper, which is the one genuine architectural win of this codebase's existing design (per the prior doc's own observation, §4) — the blast radius inside `api.ts` is contained to one function plus `login()`/`register()`, not 15 scattered `fetch()` calls.
- **Session/token invalidation during rollout:** yes, materially — every currently-issued session cookie becomes worthless the moment `CookieTransport` is removed from the running app (there's no compatibility window; a deployed frontend still holding an old cookie gets 401s until it re-logs-in and starts storing a Bearer token instead). This needs a coordinated frontend+backend deploy, or a brief user-visible "please log in again" moment — not a silent, zero-downtime cutover the way Option 1's rollout is.
- **Tests:** `apps/backend/tests/test_cookie_security.py` (currently asserts `SameSite`/`Secure` attributes on the `Set-Cookie` header) becomes entirely moot — there is no cookie to assert on — and should be deleted or fully rewritten to assert `Authorization`-header behavior instead. `test_http_auth_flow.py`'s `login()` helper (currently returns the raw `httpx.Response` and lets `TestClient`'s cookie jar carry the session forward automatically) needs to extract `access_token` from the JSON body and every subsequent authenticated call in that file (and the other ~11 files sharing this pattern) needs an explicit `headers={"Authorization": f"Bearer {token}"}` — this is the same *class* of test-suite rewrite as Option 1's, but larger, because `TestClient`'s automatic cookie-jar convenience (which Option 1 also loses per-call CSRF-header convenience on, but at least keeps cookie auth itself automatic) is fully gone here — every authenticated test call needs the header threaded through, not just an extra header on top of otherwise-automatic auth.

**The Android secondary benefit — quantified, not just mentioned:** ADR 0016 flags, as an explicit open item, that "`apps/backend`'s session-cookie auth (fastapi-users' `CookieTransport`) is workable but not the idiomatic pattern for a native app (bearer tokens usually are)." Migrating to `BearerTransport` now **fully resolves that flagged item** before it's even scoped as its own work — a genuine two-birds benefit. Concretely: a native Android client cannot participate in a browser's cookie jar or `SameSite` semantics at all; it would need to manage an HTTP client's cookie storage manually or use a Bearer token, which is the idiomatic Android/Retrofit pattern regardless of any web CSRF question. Doing this migration for CSRF reasons today means the Android work later doesn't need its own auth-transport migration — it inherits Bearer auth for free. This is a real, quantifiable removal of a whole future ADR-flagged migration, not a vague synergy claim.

#### Pros
- Structurally removes the CSRF precondition (ambient credential attachment) rather than detecting/blocking forged replays of it — closes the issue at its root cause, not its symptom.
- No new third-party CSRF-token library or its staleness/maintenance risk (Option 1's `starlette-csrf` risk, above) — everything used is already a first-party fastapi-users primitive, already a direct dependency, actively maintained (last GitHub push checked as part of this research cycle for the transport/strategy files fetched 2026-09-19, both current on `master`).
- Also resolves ADR 0016's flagged Android-readiness concern — a real, concrete secondary benefit, not just mentioned.
- Decouples transport from strategy cleanly (`BearerTransport` + `DatabaseStrategy` is supported), meaning server-side session revocation (logout, account deletion) can be *kept* rather than sacrificed for statelessness — this codebase does not have to choose between "safe from CSRF" and "can actually revoke a session."

#### Cons
- Trades cookie-based CSRF exposure for a **different**, real exposure: a Bearer token must live in JS-reachable storage, making it newly stealable via XSS in a way the current `httponly` cookie is not (developed in full above) — "safest" here means "safest against CSRF specifically," not "strictly more secure in every dimension."
- `BearerTransport` itself doesn't support logout (raises `TransportLogoutNotSupportedError`) — mitigated by keeping `DatabaseStrategy`, but this is a real detail that must be gotten right, not assumed away.
- Materially larger blast radius than Option 1: every authenticated frontend call path, the entire auth-flow test suite, and the cookie-security test file are all touched, versus Option 1's contained middleware-plus-header change.
- Forces a hard cutover (all existing sessions invalidated at deploy) rather than a compatible rollout.
- Revisits ADR 0011's explicit "session-cookie backend (not JWT)" decision — its own stated reason for that choice ("Session cookies fit a single backend server; JWT's cross-server statelessness solves a problem this app doesn't have, in exchange for refresh-token rotation and careful frontend token storage") was written *before* the cross-site-deploy reality (ADR 0016, written after 0011) existed; that original tradeoff calculus is arguably stale now, but reopening a settled ADR is process cost this option must own, not just a code change.
- No JWT refresh/rotation designed here — `JWTStrategy`'s tokens are fixed-lifetime and not renewable without a second mechanism (a refresh-token flow, or accepting that users re-log-in every `lifetime_seconds`); this is unscoped, real additional design work if long-lived sessions matter (today's cookie lifetime is 14 days, `SESSION_LIFETIME_SECONDS` in `app.py`).

#### Impact to the current baseline
- **Files:** `apps/backend/towing_backend/app.py` (transport swap), `apps/web/src/api.ts` (`request()`, `login()`, token storage), likely a new small token-storage module on the frontend, `apps/backend/tests/test_cookie_security.py` (rewritten or removed), `apps/backend/tests/test_http_auth_flow.py` and ~11 other test files sharing its `register`/`login` helpers (rewritten to carry a header, not a cookie jar).
- **ADRs:** ADR 0011 needs a formal amendment or a new ADR recording the transport change and why (mirroring how ADR 0015 already amends ADR 0011 for the async boundary) — this is a real "unwinding a previous decision" the task explicitly asked to weigh honestly, not a silent code change.
- **Frontend:** yes, substantial — `credentials: 'include'` semantics disappear, token storage and attachment become the frontend's own explicit responsibility.
- **Session invalidation on rollout:** yes, all currently-issued sessions become void the moment the transport changes; needs a coordinated deploy and a "log in again" moment for any signed-in user.

#### Time to implement
**Large — roughly 3–5 days.** Backend transport swap is small in isolation (an afternoon), but the frontend token-storage design/implementation, the full test-suite rewrite across ~12 files, the ADR amendment, and coordinated-rollout planning (avoiding a bad user experience during cutover) make this a multi-day effort, not a middleware call.

### 2b. The OWASP-aligned stateful synchronizer token (cookie-preserving alternative)

Per OWASP's Cross-Site Request Forgery Prevention Cheat Sheet (fetched directly, 2026-09-19), the canonical guidance is: "Stateful software should use the synchronizer token pattern... CSRF tokens should be generated on the server-side and they should be generated only once per user session or each request... The request should be rejected if that token was not found within the request or the value provided does not match the value within the user session." This app's session backend **is** stateful — `DatabaseStrategy` already keeps a real server-side row per login in `AccountSession`/`sessions` (`apps/backend/towing_backend/models.py`) — so this is the textbook-correct pattern for this exact architecture, not a mismatch. It would mean: adding a token column to (or a token derived from) the existing `AccountSession` row at login, handing the raw value to the frontend once, and validating it against the stored value on every state-changing request — via a `Depends()` on this codebase's own routes, plus the same middleware-vs-router-factory structural problem Option 1 already solves for the fastapi-users-owned routes (`/auth/logout`, `/users/me`), meaning this would still need to be implemented as middleware (hand-rolled, since neither `fastapi-csrf-protect` nor `starlette-csrf` ships a *stateful* variant — both default to the stateless double-submit pattern, confirmed in the prior doc §1/§5).

**Verdict for the "safest" slot: Bearer/JWT is the more defensible answer, not the synchronizer token.** Both are legitimate, OWASP-aligned-or-better answers, but they solve different-sized problems:
- The synchronizer token (2b) is a strictly more-correct **CSRF** answer than a stateless double-submit cookie (Option 1) — it ties the token to the actual session identity server-side, closing even the narrow theoretical gaps a double-submit pattern has. But it is still fundamentally a token-based mitigation layered on top of ambient-cookie auth; it does not touch the underlying mechanism (browsers still auto-attach the session cookie), and it requires **hand-rolling and personally maintaining** the validation code (no off-the-shelf library implements the stateful variant against this stack, confirmed above) — a security-sensitive piece of code this repo would own outright, which cuts against this repo's own stated posture (per the prior doc §5b) of preferring an already-reviewed implementation over hand-rolling equivalent logic.
- Bearer/JWT (2a) closes the CSRF question **and** resolves the independently-flagged ADR 0016 Android item, at the cost of the XSS-storage tradeoff and a genuinely larger migration. It is "safest" in the sense the issue's underlying concern (ambient, forgeable credential attachment) ceases to exist as a category, not just "well-defended against known attack shapes."

Given the task's own framing ("even if it means unwinding a previous decision") signals an appetite for the structurally larger fix, **and** the Android synergy is a real, freestanding reason to prefer it independent of CSRF, this document names **2a (Bearer/JWT) as the primary "safest" answer**, with 2b (stateful synchronizer token) recorded as the credible fallback if the team decides the XSS-storage tradeoff or the migration cost in 2a is unacceptable and wants to stay cookie-based while still being maximally rigorous within that constraint.

#### Risk/exposure of Option 1 and Option 3 relative to Option 2 (2a)
- **Option 1 (`starlette-csrf` alone):** closes classic CSRF completely once correctly wired, but the credential remains an ambient, browser-attached cookie — any future vulnerability class that exploits ambient cookie attachment in a way a same-origin-scoped CSRF token doesn't cover (e.g., a subdomain-takeover-adjacent cookie-scoping bug, or a bug in `starlette-csrf` itself given its 6 open issues and 3-year-stale codebase) remains a live concern in a way it structurally cannot be under Option 2. Concrete scenario: if `starlette-csrf`'s cookie comparison or `sensitive_cookies` gating logic ever has an edge-case bug (unpatched, since the project is stale), a forged request could slip through silently; under Option 2 there is no CSRF-token comparison logic to have a bug in, because there's nothing ambient to forge in the first place.
- **Option 3 (Option 1 + Origin/Referer):** same base exposure as Option 1 (still a `starlette-csrf`-mediated defense against ambient-cookie CSRF), with the Origin/Referer layer narrowing — not eliminating — the residual gap. Concrete scenario: an attack that clears or spoofs both the CSRF cookie comparison and lacks a reliable `Origin`/`Referer` (a legacy user agent, or a network intermediary stripping both headers, per OWASP's own caveat cited in the prior doc §5c) is a vanishingly narrow edge case, but it is not *zero* the way it is under Option 2, where there is no cookie-replay mechanism to bypass at all.

## Option 3 — `starlette-csrf` + Origin/Referer defense-in-depth (credible middle path)

This is Option 1 with one addition: a small Origin/Referer-verification layer (per OWASP's cheat sheet and the prior doc §5c) checked *before* or alongside the CSRF-token check, comparing the incoming request's `Origin` (falling back to `Referer`) against `settings.cors_origin` — a value `apps/backend/towing_backend/app.py` already computes and holds for CORS. This isn't a distinct architecture, it's the same middleware-based mitigation with a second, independent, nearly-free layer stacked on top — the point being that the two layers fail differently (a `starlette-csrf` implementation bug doesn't also break Origin checking, and vice versa), so a single flaw in either doesn't fully reopen the gap.

### Pros
- Same coverage guarantees as Option 1 (fastapi-users' own routes included, via middleware).
- The added Origin/Referer layer is genuinely cheap: `settings.cors_origin` is already a tracked, single, fixed value (no open set of allowed callers to reconcile against, unlike a multi-tenant app) — exactly the shape OWASP's cheat sheet calls out as making origin-checking practical, per the prior doc §5c.
- Defense-in-depth against exactly the residual risk named for Option 1 above (a bug or bypass in `starlette-csrf`'s own comparison logic) — the Origin check doesn't depend on `starlette-csrf`'s code at all, so a flaw there doesn't silently disable both layers at once.
- No additional frontend work beyond Option 1's — the Origin/Referer header is browser-attached automatically, not something `apps/web/src/api.ts` needs to set.

### Cons
- All of Option 1's cons still apply in full (staleness of `starlette-csrf`, the two-cookie `SameSite=None` requirement, the test-suite plumbing work) — this option adds work, it doesn't remove any.
- Slightly larger blast radius than Option 1 alone: one more small piece of security-sensitive code (`apps/backend/towing_backend/app.py`, a new origin-check function/middleware) to write, review, and keep correct.
- Still not "safest" by this document's own definition — it remains a mitigation layered on ambient-cookie auth, not a structural fix; the residual risk named for Option 1 above (dependency/staleness risk in `starlette-csrf`, and the ambient-cookie-theft class of exposure) is narrowed, not eliminated, by adding Origin checking on top.

### Impact to the current baseline
Identical file/test/ADR impact to Option 1, plus one additional small function/middleware in `apps/backend/towing_backend/app.py` and a couple of new unit tests asserting the Origin-mismatch-rejects-the-request behavior. No additional frontend changes beyond Option 1's own. No ADR changes. No session/cookie invalidation beyond Option 1's (none).

### Time to implement
**Small — roughly 1–1.5 days.** Option 1's ~0.5–1 day, plus a half-day for the Origin/Referer layer and its own small test coverage.

### Risk/exposure relative to Option 2
Covered together with Option 1 in the shared subsection above (both remain ambient-cookie-based mitigations; Option 3 narrows but does not eliminate the residual gap named there).

## Recommendation

This is a judgment call for a human to confirm, not a decision this document is making. With that said: **Option 1 (`starlette-csrf` middleware) is the reasonable thing to actually do first.** It fully closes the concrete, present-day exploit issue #40 describes (a forged cross-site state-changing request succeeding against a signed-in Account) within roughly a day of work, with a contained blast radius and no forced session invalidation for real users. Option 2's structural fix is the more defensible long-term architecture — especially given it also resolves ADR 0016's independently-flagged Android transport concern — but its cost (3–5 days, a hard cutover, an ADR amendment, and a newly-introduced XSS-token-theft tradeoff that needs its own careful frontend design) is disproportionate to close *this* issue alone today. The natural sequencing is: ship Option 1 now to close #40's immediate exposure, and treat Option 2 as its own future ADR-worthy decision — ideally timed to when Android work actually starts, at which point the transport migration is being paid for twice (CSRF *and* Android) rather than once, materially improving its cost/benefit case. Option 3 is worth doing as a follow-up hardening pass over Option 1 (the added Origin/Referer layer is cheap enough that there's little reason not to, once Option 1 is already in place) rather than a reason to delay Option 1's rollout.
