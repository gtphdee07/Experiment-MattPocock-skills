# CSRF protection options — closing issue #40

**Status:** research only — no decision has been made. This document exists so a human can decide how to close [issue #40](https://github.com/gtphdee07/Experiment-MattPocock-skills/issues/40) ("apps/backend: SameSite=None (required for cross-site deploy) removes implicit CSRF protection"), informed by primary-source facts as of **2026-09-19**.

**Recap of the gap (from the issue itself):** #39's fix set the session cookie's `SameSite` to `None` (paired with `Secure`) because the frontend (Cloudflare Pages) and backend (Render) deploy to different registrable domains — a genuinely cross-site relationship that `SameSite=Lax` (fastapi-users' default) breaks outright. That was necessary, but it removed the *implicit* CSRF protection `SameSite=Lax`/`Strict` used to provide. CORS (`allow_origins=[settings.cors_origin]`) doesn't help — it's a response-reading control, not a request-sending one — so a malicious page a signed-in Account visits could fire a blind `fetch(..., {credentials:'include'})` against any state-changing endpoint today. The issue itself suggests two directions: a hand-rolled CSRF-token dependency, or `fastapi-csrf-protect` "if a maintained library covers this cleanly."

---

## Summary / lean

**`fastapi-csrf-protect` is usable but not the best fit for this specific stack.** Its double-submit-cookie mechanism is real, its defaults are sane, and it is currently better-maintained by the numbers (0 open issues, a GitHub push a month ago) than the alternative below. But its integration model — a per-route `Depends()` plus an explicit `await csrf_protect.validate_csrf(request)` call inside each route's own body — cannot reach the routes that most need protection here: `PATCH /users/me` and `POST /auth/logout` are defined **inside fastapi-users' own `get_auth_router`/`get_users_router` factories** (confirmed from `fastapi_users/router/auth.py`, `fastapi_users/fastapi_users.py`), and `apps/backend/towing_backend/app.py` never sees those functions' bodies — only `app.include_router(...)` calls. There's no way to insert an explicit in-body call into code this codebase doesn't own.

**`starlette-csrf`** (also by the fastapi-users maintainer, frankie567) is a better structural fit for exactly this reason: it's ASGI middleware, so it wraps every route uniformly — including fastapi-users' own router-generated endpoints — with no per-route wiring at all. It also has a `sensitive_cookies` parameter built for precisely this situation: point it at the session cookie's name (`towing_backend_session`), and the middleware only enforces CSRF on requests that *already* carry that cookie — which naturally exempts `POST /auth/login` and `POST /auth/register` (no session cookie exists yet) while still protecting `POST /auth/logout`, `PATCH`/`DELETE /users/me`, and every Garage/Weigh-Event route once signed in. The tradeoff: `starlette-csrf`'s last PyPI release (3.0.0) is from **2023-06-27**, over three years stale, versus `fastapi-csrf-protect`'s **2025-09-16**; its GitHub repo also carries 6 open issues to `fastapi-csrf-protect`'s 0.

Both libraries' own CSRF cookie needs the **same `SameSite=None`+`Secure` treatment** as the session cookie in this deployment topology — neither is exempt from the cross-site cookie problem that created issue #40 in the first place (details in §1).

Given the maintenance gap is real but `starlette-csrf`'s code is tiny (136 lines, one file, no framework-version-sensitive surface) and it's already the fastapi-users maintainer's own recommended answer to "how do I add CSRF to fastapi-users" (§2), **the recommendation is `starlette-csrf`, with its `sensitive_cookies` option pinned to the session cookie's name** — not `fastapi-csrf-protect`, and not a hand-rolled implementation (§5 explains why hand-rolling saves little once `starlette-csrf`'s existing, tested 136-line implementation is on the table). This is a judgment call between two real tradeoffs (integration fit vs. release recency) that a human should confirm, not a slam-dunk either way.

## 1. What `fastapi-csrf-protect` actually does and how it works

**Pattern:** Stateless **Double Submit Cookie**, explicitly named as such — "Stateless implementation of Cross-Site Request Forgery (XSRF) Protection by using Double Submit Cookie mitigation pattern" (per the package's own [PyPI description](https://pypi.org/project/fastapi-csrf-protect/) and [`pyproject.toml`](https://github.com/aekasitt/fastapi-csrf-protect/blob/master/pyproject.toml)). It is **not** a synchronizer-token pattern — the library's own issue tracker confirms this explicitly: in [issue #11](https://github.com/aekasitt/fastapi-csrf-protect/issues/11) ("CSRF token validation is incomplete (does not validate uniqueness per browser session)"), the maintainer (aekasitt) responded "This is not a JWT Auth library so it is definitely not going to distinguish uniqueness per user" — i.e., by default the same token is valid for every user until it expires; there is no per-session server-side association.

**Mechanism (per [`src/fastapi_csrf_protect/core.py`](https://github.com/aekasitt/fastapi-csrf-protect/blob/master/src/fastapi_csrf_protect/core.py)):**
- `generate_csrf_tokens()` creates a random token (`sha1(urandom(64))`) and a signed version (`itsdangerous.URLSafeTimedSerializer`), returning both as a tuple.
- `set_csrf_cookie(signed_token, response)` puts the **signed** token in a cookie.
- The route handler is expected to hand the **raw** (unsigned) token to the client some other way (a rendered template context, or a JSON response body) — the raw token is *not* itself retrievable from the cookie by design, because the cookie is `httponly=True` by default (see defaults table below).
- `validate_csrf(request)` reads the signed cookie, reads a second copy of the token from a header or body field (configurable), verifies the cookie's signature/expiry via the serializer, and compares the two values with `!=` (not a constant-time comparison — worth noting, though itsdangerous's `loads()` on the signed side already does a MAC compare internally).

**Defaults (per [`src/fastapi_csrf_protect/load_config.py`](https://github.com/aekasitt/fastapi-csrf-protect/blob/master/src/fastapi_csrf_protect/load_config.py) and [`csrf_config.py`](https://github.com/aekasitt/fastapi-csrf-protect/blob/master/src/fastapi_csrf_protect/csrf_config.py)):**

| Setting | Default | Notes |
|---|---|---|
| `cookie_key` | `"fastapi-csrf-token"` | No collision with fastapi-users' `towing_backend_session` cookie or any Garage-app cookie. |
| `cookie_samesite` | `"lax"` | **Must change for this deployment** — see below. |
| `cookie_secure` | `False` | Must be `True` if `cookie_samesite` is `"none"` — enforced by a Pydantic validator (`validate_cookie_samesite_none_secure`), which raises `ValueError` at `load_config` time if violated. This is a real safety net fastapi-users' own `CookieTransport` does **not** have (it just does `"none" if settings.cookie_secure else "lax"` string logic in `apps/backend/towing_backend/app.py`, with no equivalent runtime guard). |
| `httponly` | `True` | JS cannot read this cookie's value directly — see the SameSite discussion below for why this matters for an SPA. |
| `header_name` | `"X-CSRF-Token"` | Configurable. |
| `token_location` | `"header"` | Alternative: `"body"` (form/JSON field, name set via `token_key`). A `fastapi_csrf_protect.flexible` sub-package accepts either, header taking priority — added for apps mixing server-rendered forms and API calls, per the [README](https://github.com/aekasitt/fastapi-csrf-protect/blob/master/README.md). |
| `methods` | `{"POST","PUT","PATCH","DELETE"}` | Not auto-enforced by the library itself — this set exists as a class attribute but the library never reads it inside `validate_csrf`; enforcing "only check these methods" is left to the integrator's own route wiring, since `validate_csrf` is an explicit call, not automatic method-based middleware. |
| `max_age` | `3600` seconds | Also doubles as the signed token's validity window (`time_limit` in `validate_csrf`). |

**How a route opts in:** **Dependency injection, with an explicit call inside the route body** — not a decorator, not middleware. Per the [README](https://github.com/aekasitt/fastapi-csrf-protect/blob/master/README.md)'s own canonical example:

```python
@app.post("/login", response_class=JSONResponse)
async def create_post(request: Request, csrf_protect: CsrfProtect = Depends()):
    await csrf_protect.validate_csrf(request)
    ...
```

`Depends()` only instantiates/injects the configured `CsrfProtect` object — it does **not** itself perform validation as a side effect of dependency resolution. The route function must explicitly `await csrf_protect.validate_csrf(request)`. This distinction matters a great deal for §2/§4 below: it means CSRF checking can only be added to routes whose body this codebase writes.

**Does the CSRF cookie itself need `SameSite=None` in this deployment?** **Yes — it is not exempt.** The double-submit pattern's security only works if the browser *automatically attaches* the CSRF cookie to the mutating request (that's the "double" in double submit: the same value must arrive twice, once via cookie, once via header/body, and an attacker's cross-site page can forge the header but can't read or set the victim's cookie). For the browser to attach that cookie on a cross-site `fetch(..., {credentials:'include'})` from `apps/web`'s Cloudflare Pages origin to `apps/backend`'s Render origin — the exact scenario that forced the session cookie to `SameSite=None` in #39 — the CSRF cookie needs the identical `SameSite=None; Secure` treatment. Nothing about being a "CSRF cookie" rather than a "session cookie" changes this; both are ordinary cookies subject to the same browser same-site rules. The library's own validator (above) will simply refuse to start if this is misconfigured (`cookie_secure=True` required when `cookie_samesite="none"`), which is a genuine improvement in safety over the current hand-written boolean logic for the session cookie.

One second-order consequence of `httponly=True` (the default) combined with an SPA architecture: because JS can't read the CSRF cookie directly, `apps/web`'s frontend can't just read `document.cookie` and echo the value into a header the way a typical "read XSRF cookie, send as header" recipe works. It would need a specific endpoint to hand the **raw** token to the frontend in a JSON body (see §4). This is a deliberate design choice by the library (inspired by `flask-wtf`'s server-rendered-forms model — see README: "If you were familiar with `flask-wtf` library this extension is suitable for you"), not a bug, but it is real integration work for a pure-SPA + separate-API architecture like this one.

## 2. Compatibility with fastapi-users' session-cookie backend specifically

**No integration guidance or conflict exists in either project's own tracker mentioning the other.** A GitHub code-search across all 31 issues/PRs ever filed against `aekasitt/fastapi-csrf-protect` (`state=all`, fetched via `api.github.com/repos/aekasitt/fastapi-csrf-protect/issues?state=all&per_page=100`) contains **zero** mentions of "fastapi-users" in any title or body. There is no cookie-name collision (`fastapi-csrf-token` vs. this app's `towing_backend_session`) and no reported dependency-injection conflict.

**fastapi-users' own maintainer (frankie567) has twice, directly, answered "how do I add CSRF to fastapi-users" — and named a different library both times, never `fastapi-csrf-protect`:**
- In [fastapi-users discussion #622](https://github.com/fastapi-users/fastapi-users/discussions/622) ("Do I need to deal with CSRF by myself?"), frankie567 confirmed CSRF is only relevant to cookie-based auth (not JWT-in-header), and recommended [`asgi-csrf`](https://github.com/simonw/asgi-csrf) — "It uses the double-submit cookie pattern... you have to set this same CSRF token in an HTTP header `x-csrftoken`."
- In [fastapi-users discussion #291](https://github.com/fastapi-users/fastapi-users/discussions/291) ("CSRF cookies"), a user asked fastapi-users to bundle CSRF protection itself; rather than doing that, frankie567 built and pointed people to his own separate library, **[`starlette-csrf`](https://github.com/frankie567/starlette-csrf)** — "I gave a shot at implementing a middleware for Starlette/FastAPI implementing the double-submit cookie technique."

**fastapi-users does ship CSRF machinery of its own — but only for the OAuth2 flow, which this app doesn't use.** `FastAPIUsers.get_oauth_router()`/`get_oauth_associate_router()` (per [`fastapi_users/fastapi_users.py`](https://github.com/fastapi-users/fastapi-users/blob/master/fastapi_users/fastapi_users.py)) accept `csrf_token_cookie_name`/`csrf_token_cookie_secure`/`csrf_token_cookie_samesite` parameters, defaulting `samesite="lax"`, `secure=True`, `httponly=True` — this protects the OAuth `/authorize` → provider → `/callback` redirect dance specifically, a narrower and different CSRF concern than the one issue #40 describes. `apps/backend/towing_backend/app.py` never calls `get_oauth_router`, so this machinery is irrelevant here, but it's worth knowing it exists so it isn't confused with a general answer to #40.

**The real gotcha is structural, not a documented conflict — it's about *where* fastapi-users' routes live.** `apps/backend/towing_backend/app.py` wires two of fastapi-users' pre-built routers:
```python
app.include_router(fastapi_users.get_auth_router(auth_backend), prefix="/auth", tags=["auth"])
...
app.include_router(fastapi_users.get_users_router(AccountRead, AccountUpdate), prefix="/users", tags=["users"])
```
Per fastapi-users' own source ([`fastapi_users/router/auth.py`](https://github.com/fastapi-users/fastapi-users/blob/master/fastapi_users/router/auth.py)), `get_auth_router()` returns a single `APIRouter` with **both** `POST /login` and `POST /logout` defined as closures inside that one factory function — this codebase never sees or controls those function bodies, only the resulting `APIRouter` object. The same is true of `get_users_router()`'s `PATCH /users/me`. Since `fastapi-csrf-protect`'s validation is an **explicit call inside a route body** (§1), there is no way to add it to `POST /auth/logout` or `PATCH /users/me` without either monkey-patching fastapi-users internals or wrapping them in a hand-written proxy route — neither is attractive. FastAPI's `include_router(..., dependencies=[Depends(...)])` mechanism *can* attach a dependency to every route in a router without touching route bodies, but it would apply identically to **every** route in that router — including `POST /login`, which happens before any session cookie exists, making a blanket CSRF-cookie check on that whole router a dead end (see §4 for the workaround this forces).

This is precisely the gap `starlette-csrf`'s middleware design (and its `sensitive_cookies` option) exists to close, and is the strongest concrete argument for it over `fastapi-csrf-protect` in this specific stack (details in §4/§5).

## 4. What the actual integration would look like in this codebase

**State-changing (POST/PATCH/DELETE) routes that need protection, found via `grep -rn '@router\.\(post\|patch\|delete\|put\)\|@app\.\(post\|patch\|delete\|put\)' apps/backend/towing_backend/`:**

| Route | Defined in | Owned by |
|---|---|---|
| `POST /auth/register` | `fastapi_users.get_register_router()` (called from `app.py`) | fastapi-users — but **no session cookie exists yet**, so classic CSRF (replaying an authenticated victim's cookie) doesn't apply the same way; login/registration CSRF is a different, narrower concern this doc doesn't scope in. |
| `POST /auth/login` | `fastapi_users.get_auth_router()` | fastapi-users, bundled with `/logout` in the same router — same "no cookie yet" caveat as register. |
| `POST /auth/logout` | `fastapi_users.get_auth_router()` | fastapi-users, bundled with `/login` — **needs protection** (an authenticated action). |
| `PATCH /users/me` | `fastapi_users.get_users_router()` | fastapi-users — **needs protection**. |
| `DELETE /users/me` | `apps/backend/towing_backend/app.py` (`delete_me`, this repo's own function, line ~176) | This codebase — **can** take a `Depends()`-based dependency directly. |
| `POST /trucks`, `PATCH /trucks/{id}`, `DELETE /trucks/{id}` | `apps/backend/towing_backend/profiles_routes.py` (`build_profile_router`, lines 89/119/136) | This codebase. |
| `POST /trailers`, `PATCH /trailers/{id}`, `DELETE /trailers/{id}` | `apps/backend/towing_backend/profiles_routes.py` (lines 152/184/201) | This codebase. |
| `POST /weigh-events` | `apps/backend/towing_backend/weigh_events_routes.py` (line 339) | This codebase. |
| `POST /trucks/from-photo`, `POST /trailers/from-photo`, `POST /tickets/from-photo` | `apps/backend/towing_backend/photo_ocr.py` (lines 297/309/332) | This codebase — session-authenticated (issue #20), so in scope. |
| `POST /api/evaluate` | `apps/backend/towing_backend/calculator.py` (line 129) | This codebase, but **unauthenticated by design** (ADR 0013's free calculator) — no session cookie is ever sent, so it carries no CSRF risk to add here; it already has its own per-IP rate limit (issue #38) as its abuse mitigation. |

**If using `fastapi-csrf-protect`:** every route this codebase owns (the `DELETE /users/me`, Garage CRUD, Weigh Event, and photo-OCR routes above) could add `csrf_protect: CsrfProtect = Depends()` plus `await csrf_protect.validate_csrf(request)` individually, or be gathered under one shared dependency function passed via `dependencies=[Depends(csrf_dependency)]` on each `include_router(...)` call in `app.py` (this repo already uses that router-factory pattern, so it composes naturally). **`POST /auth/logout` and `PATCH /users/me` would be left unprotected** unless a proxy/monkeypatch route is written for them specifically, which is the structural gap described in §2.

**If using `starlette-csrf` instead:** a single `app.add_middleware(CSRFMiddleware, secret=settings.secret, sensitive_cookies={COOKIE_NAME}, cookie_secure=settings.cookie_secure, cookie_samesite="none" if settings.cookie_secure else "lax")` call in `create_app()` (same file, same `settings.cookie_secure`-driven pattern the session cookie already uses) would cover **every** route above uniformly, including the fastapi-users-owned ones, with `sensitive_cookies={COOKIE_NAME}` (`COOKIE_NAME = "towing_backend_session"`, already a module constant in `app.py`) meaning the middleware only demands a matching CSRF header on requests that already carry the session cookie — so `POST /auth/login`/`POST /auth/register` (no session cookie yet) pass through untouched, and `POST /auth/logout` onward gets checked automatically the moment a session exists. No route-by-route wiring, and no risk of forgetting a newly-added route later (a real risk with the per-route `Depends()` model, since nothing forces every new mutating route to remember to add it).

**Frontend changes needed either way (`apps/web/src/api.ts`):** the centralized `request()` helper (lines 45–80) already does `credentials: 'include'` and already special-cases non-2xx responses by reading a `detail` field out of the JSON body (`ApiError`, lines 21–31) — which lines up conveniently with `fastapi-csrf-protect`'s own exception shape (`CsrfProtectError.message` surfaced as `{"detail": exc.message}` per the README's exception-handler example) and would need the same shape from a `starlette-csrf` 403 (its default `PlainTextResponse` would need a small custom exception handler to match, since `starlette-csrf` returns plain text, not JSON, by default per [`middleware.py`](https://github.com/frankie567/starlette-csrf/blob/main/starlette_csrf/middleware.py)'s `_get_error_response`). Beyond error handling, `request()` would need to:
1. Read a CSRF token from somewhere on login (a dedicated bootstrap call, or riding along on the `/auth/login` response) — for `starlette-csrf`, since its cookie defaults to `cookie_httponly=False` (per its own `CSRFMiddleware.__init__` signature), the frontend could simply read `document.cookie` for the `csrftoken` value directly, no dedicated endpoint needed; for `fastapi-csrf-protect`, whose cookie defaults `httponly=True`, a dedicated endpoint (or piggybacking on an existing authenticated `GET`) would need to return the raw token in a JSON field for the frontend to store and resend.
2. Attach that token as a header (`X-CSRF-Token` / `x-csrftoken` depending on library) on every mutating call `request()` makes — a one-line change to the shared `headers` object inside `request()` itself (line ~50), since every mutating call in `api.ts` already funnels through that one function rather than calling `fetch` directly (the two exceptions, `evaluate()` and the raw `login()`/initial calls, would need to be reasoned about individually, `evaluate()` being unauthenticated and out of scope per the table above).

## 5. Alternatives considered

**(a) A different, more "standard" CSRF library — `starlette-csrf`.** Covered throughout §§1–4 above. It is not necessarily "more standard" in the ecosystem-wide sense (`fastapi-csrf-protect` has more stars, a more recent release, and a public docs site), but it is the option the **fastapi-users maintainer himself** built and points people toward specifically for combining with fastapi-users (§2), and its middleware model plus `sensitive_cookies` parameter is the only one of the two that reaches fastapi-users' own pre-built `/auth/logout` and `/users/me` routes without extra plumbing (§2/§4). Its real cost is staleness (last released 2023-06-27, 6 open issues) — a judgment call, not a clear win either way, since the code itself is small enough (136 lines) that "unmaintained" carries less risk than it would for a larger dependency.

**(b) Hand-rolling a minimal double-submit-cookie check with no dependency at all.** Genuinely viable given how small the actual mechanism is — `starlette-csrf`'s entire implementation is one 136-line file with no dependency beyond `itsdangerous` (already in this repo's lock file at 2.2.0 for other reasons — actually, checking again: it's pulled in transitively already, so a hand-rolled version could reuse it too, or use `hmac.compare_digest` directly and skip `itsdangerous` altogether for an even smaller footprint). The case *against* hand-rolling here specifically: `starlette-csrf`'s existing code already solves the exact structural problem this app has (middleware + `sensitive_cookies` gate) in a form that's tested and has been running in fastapi-users-adjacent deployments for years per the discussion thread that produced it (§2) — writing an equivalent middleware from scratch would mostly reproduce that 136 lines with new, unexercised bugs, for a security-sensitive piece of code where subtle mistakes (non-constant-time comparison, forgetting the `Secure` flag, mishandling the `sensitive_cookies` chicken-and-egg case) are exactly the kind of thing an already-reviewed implementation has had time to shake out. Given the tradeoff is "adopt a small, stale-but-tiny dependency" vs. "hand-write and personally maintain the same 136 lines," adopting wins on this repo's stated general engineering posture (avoid deferred-decision debt, per ADR conventions elsewhere in this repo).

**(c) `Origin`/`Referer` header verification instead of tokens.** Per the [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) — a legitimate lower-effort defense-in-depth layer, not a full replacement: compare the incoming request's `Origin` (falling back to `Referer`) against the known, fixed target origin (`settings.cors_origin`, already a single hardcoded value this app tracks for CORS). This app's topology is unusually well-suited to it — a single, fixed, known Cloudflare Pages origin, not an open set of allowed callers — which is exactly the case OWASP calls out as making origin-checking practical. But OWASP's own cheat sheet lists real caveats that apply here too: `Origin` can be absent on some cross-origin redirects, `Referer` is stripped by some privacy settings and "load balancers, proxies and embedded network devices," and OWASP explicitly frames this pattern as "a defense in depth measure," not a standalone substitute for a token-based defense. It's also worth noting `apps/backend/towing_backend/app.py` already computes and holds exactly the one value (`settings.cors_origin`) this check would need, making it a genuinely cheap **addition** — but not a replacement for a real CSRF token mechanism, precisely because of the "1–2% of legitimate traffic" gap OWASP documents for header-only defenses.

**A note the research surfaced that the issue itself doesn't mention:** OWASP's cheat sheet states plainly, "Stateful software should use the synchronizer token pattern... Stateless software should use double submit cookies." This app's session backend is **not** stateless — `apps/backend/towing_backend/app.py` uses fastapi-users' `DatabaseStrategy`, backed by the `AccountSession`/`sessions` table (`apps/backend/towing_backend/models.py`), i.e., a real server-side session row already exists per login. Both libraries evaluated here default to the *stateless* double-submit pattern anyway (simpler, no schema change), which is a reasonable pragmatic choice, but a fully "by-the-book" OWASP-aligned answer would store a synchronizer token on the existing `AccountSession` row instead. Flagging this for whoever makes the final call — it's a legitimate "more correct but more work" alternative neither library ships out of the box.

**Recommendation:** adopt **`starlette-csrf`**, wired as global middleware in `create_app()` with `sensitive_cookies={COOKIE_NAME}`, over `fastapi-csrf-protect` — the fit with fastapi-users' router-factory structure (§2/§4) matters more here than `fastapi-csrf-protect`'s more recent release date, given how small and inspectable `starlette-csrf`'s actual code is. Pair it with a cheap `Origin`-header check (§5c) as defense-in-depth, not instead of it.
